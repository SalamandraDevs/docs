# Users Service and Application Module Reorganization Plan

## Goal

Replace the placeholder `POST /v1/users` implementation with a `UsersService` that owns user
application commands. Keep `Users` as the injected entity policy responsible for tenant-scoped
durable CRUD lifecycle and collection finding.

At the same time, reorganize `src/application` into one directory for each application service.
Each service directory owns its application types and Zod schemas. Shared application contracts
and configuration remain directly under `src/application`.

## Target Responsibilities

### `Users`

`Users` remains an `Entities<User>` subclass. It owns:

- tenant-scoped persistence through Core execution context;
- entity metadata generated by `Entities.create()`;
- durable user reads and collection finding;
- persistence-specific fields, including `passwordHash`.

It must never receive a raw password and must not implement password-hash policy.

### `UsersService`

`UsersService` receives `Users` and a password-hash generator through its constructor. It owns:

- application input validation and normalization that is not HTTP-specific;
- password hashing;
- initial lifecycle policy, including the initial user status;
- safe user views returned to callers;
- future user update and deletion commands that require application policy.

It must call `Users.create()` for persistence rather than recreating tenant, audit, identity,
or timestamp logic.

### Baseline execution context and public registration

`defaultTenantId` and `defaultActorId` establish the trusted baseline Core execution context
for requests that have no authenticated session. They are not an HTTP administrator and must
never grant `admin` authorization.

Two intentionally separate provisioning paths will use that baseline context:

1. A controlled bootstrap seed creates the first `active` user with `['admin']`. It is an
   operational action, not an API route or a data migration, and its credentials must come from
   an approved deployment secret rather than `local.json`.
2. The public `POST /v1/users/register` route is registered by default. Its registration can be
   disabled with `auth.publicRegistration.enabled: false` in `config/local.json`. It has no
   authentication hook and creates ordinary users under the default tenant and actor context.

Public registration is not an alternate form of `POST /v1/users`: it must not accept `roles`,
must not assign `admin`, and must not use a caller-controlled tenant or actor. It receives a
separate `RegisterUserBody` / `RegisterUserInput` containing only `username`, `email`, and
`password`. `UsersService.register()` assigns the generic `user` role and `active` status
before calling `Users.create()`.

The configured switch defaults to `true`; when explicitly disabled, the route is absent rather
than returning a disabled-feature response. Keep it in the application-level auth configuration
while this plan moves configuration to `application/config/`.

## Admin Role Authorization

Use the existing `roles` array to authorize privileged user operations. `user` is the generic
role assigned to public registrations. A trusted actor may create users, assign roles, update
users, or delete users only when its verified role collection contains the exact `admin` role.

Do not give the `tenant` role any authorization meaning in this phase. Reserve that name for
future tenant-specific operations; no route guard, default role, or policy check may use it.

Roles must be propagated through the trusted session boundary:

1. `PasswordService` and `OAuthService` read roles from the resolved durable user and include
   them in `SessionCandidate`.
2. `TokensService.issueAccessToken()` writes the roles as a signed JWT claim.
3. `TokensService.verify()` validates that claim as an array of non-empty strings and returns
   it in `SessionGrant`.
4. The authentication plugin stores the verified grant on `request.sessionGrant` as today.
5. A `requireAdminRole` route hook checks `request.sessionGrant.roles.includes('admin')` and
   throws `CustomError({ name: 'AUTHORIZATION_DENIED', ... })` when absent.

Apply `requireAdminRole` to `POST /v1/users` in this implementation. Apply it to user role
changes, updates, and deletions when those commands are implemented in `UsersService`.

Access tokens necessarily keep a role snapshot until expiry. Before role updates are
implemented, choose and document the session-revocation behavior for a role change so a removed
administrator does not retain privilege through refresh or an existing access token.

## Creation Contract

Define the user-creation application input in `application/users-service/types.ts` and its Zod
schema in `application/users-service/schema.ts`.

The input shape is the current `CreateUserBody` shape:

```ts
{
  username: string;
  email: string;
  password: string;
  roles: readonly string[];
}
```

Define a distinct public-registration input. It deliberately has no `roles` property:

```ts
{
  username: string;
  email: string;
  password: string;
}
```

Define `CreateUserInput` and its schema under `users-service`. They describe a raw-password
application command, not a durable user entity. The durable `User`, `UserStatus`, `userSchema`,
and user dataset definition stay under `entities/users`.

Define a safe `UserView` in the users-service type module. It includes public user fields and
excludes `password` and `passwordHash`:

```ts
{
  entityId: string;
  tenantId: string;
  username: string;
  email: string;
  roles: readonly string[];
  status: UserStatus;
  createdAt: Date;
  updatedAt: Date;
}
```

`UsersService.create()` returns `UserView`, not the durable `User`. This makes password-hash
non-exposure part of the application contract rather than a controller convention.

```text
src/application/
├── config/
│   ├── schema.ts
│   └── types.ts
├── contracts.ts
├── users-service/
│   ├── index.ts
│   ├── schema.ts
│   ├── types.ts
│   └── users-service.ts
├── oauth-service/
│   ├── index.ts
│   ├── oauth-service.ts
│   ├── schema.ts
│   └── types.ts
├── session-service/
│   ├── index.ts
│   ├── schema.ts
│   ├── session-service.ts
│   └── types.ts
├── tokens-service/
│   ├── index.ts
│   ├── schema.ts
│   ├── tokens-service.ts
│   └── types.ts
└── password-service/
    ├── index.ts
    ├── password-service.ts
    ├── schema.ts
    └── types.ts
```

Every listed `index.ts` is a barrel file and uses only statements in this form:

```ts
export * from "./users-service.js";
export * from "./schema.js";
export * from "./types.js";
```

Do not place `config/` inside any service directory. Keep `contracts.ts` at
`application/contracts.ts`; update its imports to use the new service modules.

Each `schema.ts` must own a service-level Zod schema; do not create temporary compatibility or
staging modules.

## Type and Schema Ownership

| Current concern                                                                        | Destination                                         | Reason                                                                                     |
| -------------------------------------------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `CreateUserRequest`, `createUserRequestSchema`                                         | `users-service/types.ts`, `users-service/schema.ts` | Raw password is an application command, not persistence state.                             |
| `RegisterUserInput`, `registerUserInputSchema`                                         | `users-service/types.ts`, `users-service/schema.ts` | Public input excludes roles; registration assigns the generic `user` role.                 |
| `admin`, `user` role constants and user-role validation                                | `users-service/types.ts`, `users-service/schema.ts` | They define user-service authorization vocabulary; `tenant` remains reserved and unused.   |
| `PasswordCredentials`, password-hash function types                                    | `password-service/types.ts`                         | They define password-service input and crypto ports.                                       |
| OAuth input, grant, identity, authorization, pending-state types                       | `oauth-service/types.ts`                            | They belong to OAuth orchestration.                                                        |
| `SessionCandidate`, `Session`, `SessionView`                                           | `session-service/types.ts`                          | They describe session orchestration and returned session views.                            |
| `AccessToken`, `RefreshToken`, `BearerToken`, `SessionGrant`, signing-key public types | `tokens-service/types.ts`                           | They define token issuance, verification, and key-facing contracts.                        |
| Durable `User`, `SessionRecord`, entity schemas, dataset definitions                   | `entities/users` and `entities/sessions`            | They are persistence/entity policy concerns.                                               |
| Fastify route path/query schemas and response envelopes                                | `api/routes/...`                                    | They remain HTTP/OpenAPI concerns and import service-level input schemas when appropriate. |

The service-level schemas validate reusable application inputs. Route schemas may compose them,
but application modules must not import Fastify route types, Fastify instances, or reply
objects.

## Implementation Steps

### 1. Establish the service module layout

1. Create the five service directories and their barrel `index.ts` files.
2. Place `OAuthService`, `SessionService`, `TokensService`, and `PasswordService` directly in
   their owning service directories.
3. Define the former `application/auth/types.ts` concerns in the owning service `types.ts`
   modules according to the ownership table, then remove `application/auth`.
4. Define each service-level Zod schema in its matching `schema.ts` module.
5. Update all internal imports, API imports, infrastructure imports, bootstrap imports, and
   `contracts.ts` imports to use the new modules or their barrels.
6. Remove the old flat implementation and type files in the same change set.

This is a clean replacement, not a migration: do not retain legacy paths, compatibility
exports, fallback imports, compatibility types, or dual implementations. Complete the
reorganization before adding user-creation policy.

Define `SessionCandidate` and `SessionGrant` with their new `roles` fields in their owning
session/token service type modules. Update all affected interfaces and imports in
`contracts.ts`, session creation, password authentication, OAuth resolution, token issuance,
token verification, and Fastify request augmentation.

### 2. Add password-hash generation

1. Add `generate(password: string): Promise<string>` to `PasswordService` and its application
   contract. It returns a PHC-encoded Argon2 password hash.
2. Implement `PasswordService.generate()` with Argon2 next to the existing verifier behavior in
   `password-service/password-service.ts`.
3. Use explicit Argon2 options if the product has approved password-cost policy; otherwise
   retain the library defaults only as an acknowledged interim decision.
4. Construct `PasswordService` first and inject that service into `UsersService` from
   `bootstrap.ts`.
5. Keep raw passwords local to the creation command. Do not log, persist, return, or put them
   in an error cause.

### 3. Implement `UsersService`

1. Create `UsersService` in `users-service/users-service.ts` with constructor dependencies:

   ```ts
   constructor(
     private readonly users: Users,
     private readonly passwordService: PasswordService
   ) {}
   ```

2. Add `create(input: CreateUserInput): Promise<UserView>`.
3. Add `register(input: RegisterUserInput): Promise<UserView>`. It uses the same hashing and
   safe-view mapping as creation, but fixes the public role collection to `['user']` and status
   to `active`.
4. Validate or parse the application input using the users-service schema at this service
   boundary when the caller is not already schema-validated.
5. Generate the durable password hash with `this.passwordService.generate(input.password)`
   before building a durable create record.
6. Validate role input according to the users-service role schema. Recognize `admin` as the
   privileged role and `user` as the generic role; do not introduce `tenant` as a recognized
   role or default.
7. Call `users.create()` with `username`, `email`, `passwordHash`, `roles`, and the chosen
   initial status.
8. Map the created durable user to `UserView`. This mapping is not a convenience wrapper: it is
   the security boundary that removes password-hash material.

The controlled bootstrap administrator and publicly registered user are both `active`. The
current session authentication permits only active users, so a registration creates a usable
account without a verification or approval workflow.

### 4. Wire `UsersService` through bootstrap and API services

1. Construct `Users` from the CRUD adapter as today.
2. Construct `PasswordService` and then construct `UsersService(users, passwordService)` in
   `bootstrap.ts`.
3. Add `usersService: UsersService` to `ApiServices` while retaining `users: Users` for current
   collection/read operations.
4. Do not add pass-through CRUD wrappers to `UsersService`. Future methods belong there only
   when they add validation, transformation, authorization, or lifecycle policy.

### 5. Implement administrator creation and public registration

1. Keep the Fastify body type as `CreateUserBody`; it is the API transport contract.
2. Make `CreateUserBody` use the application input shape without creating a rename-only type
   alias.
3. Replace the placeholder error with:

   ```ts
   const user: UserView = await request.server.services.usersService.create(request.body);

   void reply.code(201).send(toUserResponse(user));
   ```

4. Update `toUserResponse` to accept `UserView`, converting its date values to ISO strings.
5. Retain the existing `201` response schema. It already models the safe public user response.

For public registration:

1. Add `publicRegistration: { enabled: boolean }` to the application auth configuration type
   and schema, with `true` as its default.
2. Allow `config/local.json` to set `auth.publicRegistration.enabled` to `false` when public
   registration must be unavailable in that environment.
3. Add `publicRegistrationEnabled` to `RoutesOptions` and propagate it through API and v1 route
   registration.
4. Register `POST /v1/users/register` only when that option is true. It must not use
   `requireAuthenticatedUserPolicyContext` or `requireAdminRole`.
5. Give the route a strict `RegisterUserBody` schema with no `roles`, then call
   `request.server.services.usersService.register(request.body)` and return the same `201`
   `UserResponse` view.
6. Apply a route-specific rate limit before enabling this endpoint outside local development.

### 6. Add conflict and authorization policy

The user dataset already enforces tenant-scoped unique usernames and emails. Core raises
`DB_DUPLICATE_KEY_ERROR`; map it in the auth error plugin to a `409 Conflict` problem and add
`409` to `userProblemResponses`.

Add `requireAdminRole` after the existing authenticated user policy context hook for
`POST /v1/users`. It must authorize the verified `SessionGrant.roles`, never roles submitted in
`CreateUserBody`. Do not silently allow every authenticated tenant user to create users or
self-assign the `admin` role.

## Verification

1. Run `pnpm run build` in `tools` and `core` when their generated package outputs are changed.
2. Run `pnpm run check` in `services/auth` after each implementation stage.
3. Run the service lint command after the refactor and address violations introduced by this
   implementation before expanding scope.
4. Manually create a user as an authorized actor and confirm a `201` safe user response without
   raw password or password hash.
5. Confirm duplicate username and duplicate email requests return `409`.
6. Confirm a non-admin authenticated actor receives `403` when creating a user.
7. Confirm an authenticated actor with `admin` in the verified access-token roles can create a
   user and assign allowed roles.
8. Confirm a newly active user can authenticate through the existing password session flow.
9. Confirm the bootstrap seed creates the first active administrator without exposing a public
   bootstrap route.
10. With public registration disabled in `config/local.json`, confirm `POST /v1/users/register`
    is absent.
11. With the default enabled setting, confirm public registration returns `201`, cannot submit
    roles, creates an active user with `['user']`, and cannot create an administrator.
12. After completing the build, checks, linting, and manual verification, reread `../AGENTS.md`
    and perform one final code-compliance review. Correct any deviation from its applicable
    instructions, then rerun only the verification affected by that correction.

No automated tests are included in this plan. Add them only when explicitly requested.
